# Project documentation style

Use American English and the terminology used by current OpenShift and NVIDIA documentation.

Apply the [Red Hat supplementary style guide](https://redhat-documentation.github.io/supplementary-style-guide/) when it covers a style or terminology question. Use [Vale at Red Hat](https://redhat-documentation.github.io/vale-at-red-hat/docs/main/user-guide/introduction/) when Vale is available and configured for Markdown.

Use these writing rules:

- Lead with what the reader can do or understand.
- Use active voice when the actor matters.
- Use one term for one component or action throughout a document.
- Use direct verbs instead of noun forms of actions.
- Keep procedures sequential and put one primary action in each step.
- State requirements with `must`, recommendations with `should`, and possibilities with `can` or `may`.
- Define project-specific terms on first use.
- Keep paragraphs focused on one topic.
- Use lists for parallel items and procedures. Use tables for comparisons and field reference.
- Preserve exact commands, identifiers, YAML keys, enum values, units, and searchable error text.
- Avoid promotional adjectives and claims that the evidence does not measure.

Use strict simplified technical English for procedures, warnings, and recovery steps. Use an STE-flavored edit for explanations and README prose. Sentence-length targets are aids, not requirements. Keep a longer sentence when splitting it would change or obscure a condition.

After editing, compare the source claim inventory with the final text. Preserve every condition, exception, scope limit, and degree of certainty.
